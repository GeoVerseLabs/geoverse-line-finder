# Upgrading

🌐 [简体中文](UPGRADING.md) ｜ English

## From 0.2.0 to the next release (multi-level)

Networks that do not use `group` are unaffected: with default options the output is still bit-identical to 0.1.0. The changes below only concern connectivity groups, snap constraints and `connectors: 'legs'`.

| Change                                                                         | Who is affected                                                      | What to do                                                                                                                                                                |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Connector **interiors no longer belong to the start floor**                    | Code locating staircase steps with `mode: 'exact'` or `findVertex()` | Use the coordinates of the staircase's two ends; a step never belonged on a floor (it let the floor shortcut into the stairs)                                             |
| A `group`-constrained snap **scans only that group**                           | Anyone relying on the old, broken crowding-out behaviour (unlikely)  | Normally a fix: three floors used to be enough for a false `SNAP_FAILED`. The result matches a full scan with the same constraint and no scan limit                       |
| New failure detail `detail: 'SCAN_LIMIT'`                                      | TypeScript code with an exhaustive `switch` on `detail`              | Add a branch; it used to be reported as `FILTERED`                                                                                                                        |
| Candidate `group` is `undefined` in the middle of a staircase                  | Code reading `candidate.group` to tell the floor                     | The middle of a staircase really is on no floor; select stairs with `featureIds` or `filter`                                                                              |
| With `connectors: 'legs'`, `sections[].start/end` now shift with the connector | Code indexing `leg.path` with those values                           | This is a fix: they used to point at the wrong coordinates. `sections` / `transitions` / `levels` now all match `leg.path`                                                |
| `GRAPH_FORMAT_VERSION` changed from `1` to `2`                                 | Code asserting `data.formatVersion === GRAPH_FORMAT_VERSION`         | Graphs without level semantics still write `1`; to test readability use the new `GRAPH_FORMAT_VERSIONS.includes(v)`                                                       |
| `WeightContext` gains `fromGroup` / `toGroup` / `rise`                         | Tests that build a `WeightContext` literal by hand                   | Add the three fields; weight functions themselves are unaffected                                                                                                          |
| `graph.features` grows when `verticalConnectors` is used                       | Code mapping `featureIndex` back to the input collection             | The synthesised features are appended after the input; `stats.verticalConnectors` counts them, and deserialising with the input features brings them back from the header |

**To switch multi-level on** (none of it is required — without `levels` everything stays as it was):

1. add `levels` with an `ordinal` (and optionally an `elevation`) for every floor group;
2. make sure there is **no free way to change level** — give zero-length lifts a fixed positive cost, or the level bound degenerates to 0;
3. run `graph.diagnostics()` once and read `connectorEnds` and `missingOrdinals`;
4. declare lifts through `verticalConnectors` so the boarding cost is not charged per floor.

See [Multi-level routing](MULTI_LEVEL.en.md).

## Upgrading from 0.1.0 to 0.2.0

## Default options: unchanged output

Without new options, `route()` / `findPath()` / `nearest()` return results that are **bit-identical** to 0.1.0: `path`, `weight`, `distance`, `legs` (including the engine statistics `settled` / `relaxed`), the existing `waypoints` fields, and the `reason` / `message` / indices of failures. `test/golden.test.ts` pins this with golden outputs generated by 0.1.0 on the GPF networks, random grids, the synthetic warehouse and the 135k-coordinate OSM network.

Result objects only **gain fields** (`networkWeight`, `skipped`, `waypoints[i].relocation`, `sections[i].fromMeasure` and so on), so existing reads keep working.

## Behaviour changes

| Change                                                                                                                              | Who is affected                                              | What to do                                                                                                |
| ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| With a geographic metric, coordinates outside `[-180, 180] × [-90, 90]` or segments crossing ±180° throw `RangeError` at build time | users passing projected coordinates to the default haversine | use `metric: 'euclidean'` for projected coordinates; 0.1.0 computed wrong distances for such input anyway |
| `stats.danglesSnapped` also counts dead ends lying exactly on a segment (zero gap)                                                  | users asserting on or reporting that count                   | use the new count; connectivity itself is unchanged                                                       |
| `RouteFailureReason` gains `'ALL_SKIPPED'` and `'BUDGET_EXCEEDED'`                                                                  | TypeScript code with an exhaustive `switch` on `reason`      | add the two cases; they only occur with `onFailure: 'skip'` or a `budget`                                 |
| `SnapConnectivity` gains `'reachable'`                                                                                              | code exhaustively matching that type                         | as above                                                                                                  |

## Custom engines

The `PathAlgorithm` / `SearchGraph` contract is backward compatible and engines written for 0.1.0 keep working. Note that:

- The overlay is no longer limited to 8 edges and 2 virtual nodes, so `nodeCount` and the overlay arrays may change and be reallocated between queries. **Read them at the start of every `search`** (as 0.1.0 engines already did) and do not cache them across queries.
- Every new optional field has a fallback: for engines without `capabilities.multiTarget`, optimal selection and one-to-many run one search per target; for engines without `capabilities.budget`, `maxCost` is checked by the library on the result and `maxSettled` has no effect.
- A heuristic may now return `Infinity` (ALT proved the node cannot reach the target); treat it as "do not queue". Treating it as an ordinary number is still correct.

## TypeScript

The declarations compile with TypeScript 5.0–5.9 and `skipLibCheck: false` (0.1.0's needed 5.7 or later).

## Using the new capabilities (warehouse picking routes as an example)

1. **Waypoints must not be moved**: `snap: { connectivity: 'nearest', maxDistance: 100 }`, or keep the default and set `maxRelocation`.
2. **A location is only reachable from the aisle it faces**: per waypoint `{ coordinates, snap: { featureIds: [aisleId] } }`; put aisle-level preferences into the weight, never into a filter.
3. **Choose the access aisle by total cost**: `snap: { selection: 'optimal', costMode: 'arrive-depart', maxRelocation: 20 }`, with `totals.includeSnapWeight` so that `weight` includes snap costs.
4. **Unreachable waypoints**: `onFailure: 'skip'` (multi-point planning) or `'straight'` (history tracks, heat maps).
5. **Distances that include connectors on every leg**: `connectors: 'legs'` + `totals.includeConnectorDistance`.
6. **Heat maps in 10 m pieces**: `sectionsDetail: 'measure'` and bucket by `floor(measure / 10)`.
7. **Data quality checks**: build with `diagnostics: true` and read `graph.diagnostics()`.
8. **Overlapping floors**: `group` by floor, elevators as connector features with `zeroWeight: 'free'` or a fixed weight.
9. **Several threads**: `graph.toTransferable()` on the main thread, `RoutingGraph.fromTransferable()` in the worker.
