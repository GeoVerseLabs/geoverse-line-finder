# 基准与正确性实测

> 2026-09-11 · Intel Core Ultra 9 185H · Node v22.12.0 · `NODE_OPTIONS=--expose-gc` · 每个场景 5 轮 + 1 热身，每轮从零构建并轮换执行顺序 · 数据为 geojson-path-finder 自带的测试路网。
> 表中为**中位数 [最小–最大]**；两组区间重叠的差异视为噪声，不下结论。复现：`pnpm bench`（`--only osm` 可单跑一个场景）。

## 参赛方

| 名称                      | 配置                                                                                                     |
| ------------------------- | -------------------------------------------------------------------------------------------------------- |
| geoverse A* / Dijkstra    | `snap.mode: 'exact'`，与对手一样要求输入是路网顶点                                                       |
| geoverse A\* + edge snap  | 默认线段吸附：每个途经点多一次 R 树最近邻 + 叠加层                                                       |
| geojson-path-finder 2.1.0 | `tolerance: 1e-9`，保持与其他库相同的拓扑（仅完全相同的坐标相连）                                        |
| terra-route 0.0.18        | A\* + ALT 地标（第 256 次查询后启用）；不支持权重，只参加最短距离场景，代价由其返回几何按 haversine 重算 |

"非最短"列 = 该库代价高于所有参赛方中最优值的点对数（相对误差 1e-6）。本库在测试里与独立裁判逐对相等（见 `test/gpf-parity.test.ts`），所以这一列非零即说明该库给出了非最短路。

## 1. network.json — 最短距离

44 条线、932 坐标，压缩后只剩 17 个节点。

| 库                       | 初始化 ms         | 300 次路由 ms      | 单次 µs p50 / p95 | 找到 | 非最短 |
| ------------------------ | ----------------- | ------------------ | ----------------- | ---- | ------ |
| geoverse A\*             | 1.9 [1.7–2.9]     | 12.9 [10.9–15.6]   | 34 / 110          | 300  | 0      |
| geoverse Dijkstra        | 1.8 [1.2–2.6]     | **8.3** [7.1–13.8] | 21 / 74           | 300  | 0      |
| geoverse A\* + edge snap | 1.5 [1.2–2.1]     | 21.0 [17.9–23.6]   | 47 / 142          | 300  | 0      |
| geojson-path-finder      | 10.6 [8.9–11.5]   | 20.5 [18.4–24.5]   | 60 / 117          | 300  | 0      |
| terra-route              | **0.4** [0.4–0.7] | 17.6 [16.0–19.2]   | 38 / 169          | 300  | 0      |

图极小时 A\* 的启发式开销划不来，Dijkstra 最快；两者都与 terra-route 区间不重叠。线段吸附在这里占了单次查询的大头（两次最近邻 + 叠加层 ≈ 27 µs）。

## 2. large-network.json — 最短距离（所有道路类型）

20120 条线、13.5 万坐标（哥德堡 OSM，基准前滤掉 107 个面要素）。

| 库                       | 初始化 ms               | 300 次路由 ms             | 单次 µs p50 / p95 | 找到 | 非最短 |
| ------------------------ | ----------------------- | ------------------------- | ----------------- | ---- | ------ |
| geoverse A\*             | 310.0 [283.5–350.0]     | **306.3** [287.0–337.0]   | 705 / 2948        | 300  | 0      |
| geoverse Dijkstra        | 304.1 [248.5–353.1]     | 692.7 [681.6–733.7]       | 2282 / 4824       | 300  | 0      |
| geoverse A\* + edge snap | 207.1 [194.7–301.4]     | 327.3 [310.4–377.1]       | 781 / 2975        | 300  | 0      |
| geojson-path-finder      | 2798.3 [2724.1–2869.1]  | 11574.0 [11431.0–12882.6] | 39143 / 80185     | 300  | **41** |
| terra-route              | **112.8** [105.6–118.9] | 1410.8 [1291.2–1433.2]    | 2964 / 13280      | 300  | 0      |

- 路由：A\* 比 terra-route 快约 4.6 倍、比 geojson-path-finder 快约 38 倍，区间均不重叠；比本库 Dijkstra 快约 2.3 倍。
- 初始化：比 geojson-path-finder 快约 9 倍；比 terra-route 慢约 2.7 倍——本库多做了权重、链压缩、连通分量、A\* 嵌入与 R 树。
- 前三行的初始化是**完全相同的代码**，中位数却在 207–310 ms 之间摆动：这正是"单轮数字不能下结论"的现场证据。线段吸附相对 exact 的路由差（327 vs 306）区间重叠，同样不下结论。
- geojson-path-finder 即使在**纯距离**权重下也有 41/300 对非最短，根因见 §4。

## 3. large-network.json — OSM 通行时间、单向（geojson-path-finder 自带测试权重）

权重函数原样移植自 geojson-path-finder 的 `test/osm-weight.js`（`bench/osm-weight.ts`），双方调用同一个函数；点对从该权重下的最大连通分量里抽样。

| 库                       | 初始化 ms              | 300 次路由 ms           | 单次 µs p50 / p95 | 找到 | 非最短 |
| ------------------------ | ---------------------- | ----------------------- | ----------------- | ---- | ------ |
| geoverse A\*             | 264.9 [176.7–268.4]    | **206.0** [195.8–215.0] | 552 / 1678        | 293  | 0      |
| geoverse Dijkstra        | 261.0 [190.2–413.9]    | 285.4 [266.8–288.4]     | 880 / 1871        | 293  | 0      |
| geoverse A\* + edge snap | 229.8 [182.9–262.0]    | 226.7 [213.0–252.7]     | 633 / 1737        | 293  | 0      |
| geojson-path-finder      | 2708.8 [2675.5–2768.0] | 6678.5 [6574.8–6764.8]  | 21498 / 43935     | 293  | **42** |

- 时间权重下启发式按"全网最快车速"缩放、比距离场景弱，A\* 仍比 Dijkstra 快约 1.4 倍（区间不重叠），比 geojson-path-finder 快约 32 倍。
- **吸附的价值**：最初一版基准误从"所有道路类型"的分量里抽点，大量点落在被该权重判为不可通行的人行道上——exact 模式只有 74/300 能路由，默认线段吸附把这些点挪到最近的可通行道路，292/300 能路由。

## 4. geojson-path-finder 非最短路的根因实验（`pnpm bench:gpf`）

同一批 60 个随机点对（OSM 时间权重），与不共享任何代码的朴素裁判（未压缩有向图 + Dijkstra）比较：

| 变体                                                        | 非最短 |
| ----------------------------------------------------------- | ------ |
| geojson-path-finder 2.1.0 原版                              | 7      |
| 同一库的 Dijkstra 跑它**未压缩**的顶点图                    | 0      |
| 只放宽 `compactor` 里一行守卫（允许更便宜的旁路替换已有边） | 0      |
| geoverse-line-finder                                        | 0      |

| 点对 | 裁判 (s) | geojson-path-finder | 未压缩图 | 单行补丁 | geoverse |
| ---- | -------- | ------------------- | -------- | -------- | -------- |
| 6    | 686.5    | 687.7 (+0.18%)      | 686.5    | 686.5    | 686.5    |
| 23   | 280.1    | 281.3 (+0.44%)      | 280.1    | 280.1    | 280.1    |
| 33   | 232.9    | 233.0 (+0.02%)      | 232.9    | 232.9    | 232.9    |
| 46   | 446.6    | 449.3 (+0.62%)      | 446.6    | 446.6    | 446.6    |
| 52   | 587.4    | 604.4 (+2.89%)      | 587.4    | 587.4    | 587.4    |
| 53   | 453.8    | 454.2 (+0.09%)      | 453.8    | 453.8    | 453.8    |
| 56   | 437.5    | 440.3 (+0.63%)      | 437.5    | 437.5    | 437.5    |

结论：geojson-path-finder 压缩度 2 顶点时，`if (!neighbor[otherNeighborKey] && weightFromNeighbor)` 只在两邻点间**没有边**时才添加旁路；已有更贵的边（平行道路、单向对向车道、或先前压缩出的更长链）时，更便宜的旁路被丢弃，最短路从压缩图里消失。用裁判重算它返回的路径恰好等于它报出的权重——路径合法，只是不是最短。2.0.2 与 2.1.0 为同一行代码。
